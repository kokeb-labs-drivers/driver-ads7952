Detailed Description

template<SpiPort Port>
class ads7952::ADS7952< Port >

Driver for one ADS7950, ADS7951, ADS7952 or ADS7953 on a platform port.

Lifecycle: construct with the configuration (no I/O), then EnsureInitialized(), the one way to start (bus up, reset, configuration written, identity check), use, optionally Deinitialize(). Every call that touches the chip returns Error::NotInitialized until EnsureInitialized() has succeeded; no call starts the chip as a side effect.

The frame pipeline. A channel chosen in frame N is acquired in frame N + 1 and its result comes back in frame N + 2 (Figures 51, 53, 56); a range written in frame N applies from the result of frame N + 2 as well. The driver keeps track of what the chip is doing (mode, channel, replies still in flight), so a call sends only the frames it needs, and it checks the channel address of every reply it returns: a result is never attributed to the wrong channel.

A reset behind the driver's back (a brown-out) puts every register back to its reset value (section 8.4.3, Table 11, section 8.5.3) and makes the next conversion invalid (section 7.6); the chip has no flag for it. The driver checks the address of every reply it can predict, the ones a new select discards included, and a reply from channel 0 (the power-on channel) where it expects another is DeviceReset. After it, and after any ChannelMismatch or SequenceMismatch, the driver is uninitialised (fail-safe): EnsureInitialized() resets and programs the chip in the datasheet order and discards the invalid first conversion. A reset at any moment the chip rests on channel 0 in Manual mode (after a read of channel 0, a list ending with it, in any mix of reads) shows in no reply, and the results right after a reset (the invalid conversion, one in Range 1) can be returned before it is seen. Mitigations: the opt-in Config::park_channel, and ApplyConfig(), which writes every register whatever the driver's copy says (docs/limitations.md).

◆ ApplyConfig()

template<SpiPort Port>
Result< void > ads7952::ADS7952< Port >::ApplyConfig ( const Config &  config)
noexcept

Replace the configuration.

Before the start it only stores it, with no I/O. On a running driver it writes every register, changed or not, in the order of section 8.4.3: the GPIO program register, the Auto-1 and Auto-2 program registers, every alarm threshold of every group (Table 13), then a mode word with the range and the GPIO levels and the frame on which the outputs change. The driver's copy is never trusted, because no register can be read back and a reset while the chip converts channel 0 shows in no reply: ApplyConfig(GetConfig()) puts the whole configuration back. 6 + 10 frames per alarm group (36 on the ADS7952). vref_mv and va_min_mv are never sent.

Parameters
configChecked with Validate().
Returns
Ok, InvalidArgument (it fails Validate(), or it changes the variant or package of a running driver; nothing sent), Unsupported, or Bus. After Bus the stored configuration is unchanged and the chip may hold part of the new one: restart with Deinitialize() and EnsureInitialized().

Prove the scale now: one conversion of the Config::monitor channel, judged by CheckScaleCode(). An explicit, opt-in call: nothing on the conversion path runs it.

Costs what ReadChannel() of that channel costs (1 to 3 frames) and leaves the chip in Manual mode on it, so the next ReadAuto1() enters Auto-1 again (two frames). Its select carries the range, so it proves that the chip takes the range the driver sends and that the reference is there; a range lost during a long Auto-1 run shows in the scan itself: check the monitor's code of each Bank with CheckScaleCode(), which costs no frame.

Returns
The monitor's code; or NotInitialized, InvalidArgument (no monitor; nothing sent), Bus, ChannelMismatch, RangeMismatch, ScaleMismatch or DeviceReset (a reply from channel 0 out of turn, or Range 1 where the driver sends Range 2: the reset value of DI06). After any of these but Bus the driver is uninitialised (fail-safe).

◆ EnsureInitialized()

template<SpiPort Port>
Result< void > ads7952::ADS7952< Port >::EnsureInitialized ( )
noexcept

Reset the chip, write the configuration and check that an ADS795x answers, once: the only way to initialise the driver.

In order: Validate() the configuration (no I/O), bring the bus up, end any program sequence an earlier failure left open (two frames), reset every register (the GPIO program frame with DI09 = 1, then the frame in which the chip resets itself, then kPowerUpUs), write the GPIO, Auto-1 and Auto-2 program registers and every alarm group that differs from its reset value, then the identity check: in Manual mode, select a channel, keep it one frame, select a second one whose address differs in every bit (10 and 5 on the ADS7952), and demand that the replies two frames after each carry exactly those addresses. A MISO line stuck low or high, a fixed reply pattern, a loop-back and an SDI line that does not reach the chip (whatever mode the chip was left in) all fail it. With a Config::monitor, last, the scale check: one conversion of the monitor channel must fall in its window (CheckScaleCode()), which proves the range and the reference before any result is returned. The chip is left in Manual mode. After it succeeds, later calls return Ok at once with no I/O; after it fails, the next call starts again from the beginning.

Returns
Ok, InvalidArgument or Unsupported (the configuration fails Validate(); no I/O), Bus, NoDevice (every identity reply 0xFFFF), DeviceIdMismatch, or RangeMismatch or ScaleMismatch (the scale check).

◆ ReadAuto1()

template<SpiPort Port>
Result< Bank > ads7952::ADS7952< Port >::ReadAuto1 ( )
noexcept

One pass of the Auto-1 sequence (Config::auto1_channels): the hot path.

While the chip runs the sequence (after a previous ReadAuto1()), k frames for k channels, each the Auto-1 word with DI11 = 1 and DI10 = 0 (the range and GPIO levels again, no restart): the chip steps through the sequence by itself and every reply is a result. Unlike a "continue" word, it puts the range back and, after a reset, makes the chip enter Auto-1 with the reset sequence, so even a sequence of channel 0 alone shows the reset within a few passes. Right after SetRange() or SetAuto1Channels(), k + 1; otherwise the Auto-1 word that enters the mode and restarts the sequence (with the range and the GPIO levels) and one frame in flight come first, k + 2. The k replies must be the k channels of the sequence, each once, in the chip's ascending, wrapping order; the pass may start at any channel.

Returns
The bank, or NotInitialized, Bus, DeviceReset (a reply from channel 0 out of turn: the chip is back in Manual mode on channel 0) or SequenceMismatch (the chip left Auto-1 or lost its mask). After either of the last two the driver is uninitialised: call EnsureInitialized().

◆ ReadChannel()

template<SpiPort Port>
Result< uint16_t > ads7952::ADS7952< Port >::ReadChannel ( uint8_t  channel)
noexcept

One conversion of channel in Manual mode.

When the chip already converts channel in Manual mode (after a ReadChannel() of the same channel, or a ReadChannels() that ended with it), one frame; right after SetRange(), two (the first reply was converted in the old range); otherwise three: the Manual word that selects channel (with the range and the GPIO levels, DI11 = 1), the frame that acquires it, and the one that returns it. The frame that returns the result is the Manual word for channel again, so every read sends the channel and the range a reset would have changed (section 8.4.3). The reply's address must be channel; after a select from a settled channel the two replies discarded must carry that channel.

Parameters
channel0 to GetChannelCount() - 1.
Returns
The 12-bit code, or NotInitialized, InvalidArgument (nothing sent), Bus, DeviceReset (a reply came from channel 0, the power-on channel) or ChannelMismatch (another address). After either of the last two the driver is uninitialised: call EnsureInitialized().
